# 08 越权与 IDOR

> 性价比第一的洞型：最适合手工检测、几乎每个业务系统都有、请求与正常访问无异（无特殊字符，WAF 和日志基本发现不了——这也意味着遍历即变相脱裤）。

## 分类

| 类型 | 定义 | 测试 |
|------|------|------|
| 水平越权（平行） | 类型不变，ID 变 | id:110（自己）→ id:120（他人）成功 |
| 垂直越权 | ID 不变，类型变 | id:001（管理员）也成功 |
| 交叉越权 | 都变 | 组合 |

## 三步法

1. **定位鉴权参数**：不只看 URL——cookie 的 uin（腾讯系）、body 明文字段（京东 pin）、http 头 token、REST 路径段（`/api/orders/287789`）都可能是身份标识
2. **替换**：准备两个账号（A/B 对照），A 的请求换成 B 的身份参数
3. **多 ID 证明**：遍历多个 id 证明危害面（截图多几条）

**工具**：Burp 插件 Authz / AuthMatrix / Autorize（自动对比不同用户的响应）；双账号双浏览器互测。

## 标识符猜测（IDOR 深入）

- 数字递增/递减：`/api/orders/287789 → 287790`
- 用户名/邮箱明文；Base64 编码标识符
- **弱伪随机**：UUID v1 含时间戳可预测；MongoDB ObjectId 含时间戳+机器ID+计数器
- 哈希参数：MD5/SHA1 可撞
- 通配符：`/api/users/*`、`/api/users/%`、`/api/users/_`

## 请求操纵技巧

- 切换 HTTP 方法：`POST → PUT`
- 修改 Content-Type：`XML → JSON`
- 值转数组：`{"id":19} → {"id":[19]}`（**经常绕过校验**）
- 参数污染：`user_id=A&user_id=B`

## 国产业务实战套路（JSRC 归纳）

### 空值绕过
多参数匹配查询（`userId=1111&userIdCard=340...`）时，**把辅助参数置空或整段删除**，看能否仅凭单参数遍历；前端限定时间段的（只查 3 个月），改时间区间或对时间参数赋空。

### 签名跨包绕过
1. 先试签名参数值**置空**，看是否校验
2. 追签名 key 的来源——若 key 来自**上一个请求的返回值**，篡改上一包响应中的 key，让 API 主动取用假 key 完成绕过

### 流程阶段跳转（找回密码类）
开发者的假设："进到第二步说明第一步已验证"。直接抓包跳到最后一步，把账号参数换成受害者——**分段流程进入下一段不再回验身份**是最高发的缺陷模式。

### 后台提权三线
- 改权限组 id（管理员通常 0 或 1）
- "按 userid 改密码"处改 id → 改管理员密码
- 个人资料插 XSS → 打管理员 cookie

### 两个具体 bypass
- 页面 403 但加 `X-Forwarded-For: 127.0.0.1` 即绕过
- 后台 POST 参数 `verifycode2` 改名为 `verifycode` 绕验证码策略

## 自动化思路（写扫描器时用）

- **id 型越权**：爬取收集带 id 参数的 URL，设阈值 N，id 遍历 N 次返回结果不一致则告警，人工分析+白名单处理误报
- **垂直越权**：按业务建角色访问控制模型，不同级别账户 Cookie 交叉请求，不满足模型的告警

## 白盒检查清单

所有功能函数是否做权限判断、是否依赖不可信数据（数据库/cookie/用户输入）、参数是否加密。修复范式：前端不传身份标识、后端从 session 取、uuid 代理主键。

## writeup 实证要点

- **错误消息是金矿**：无效值常返回有效值列表（Airbnb 传无效 template 返回全部模板列表；Facebook 无效 payment_type 返回全部支付类型）
- **新功能 = 新漏洞**：新上线的 API 没经过加固
- **写操作（删除/修改）往往比读操作更容易找到**
- **移动端 API 通常比 Web 防护弱**
- **跨应用 IDOR**：同一 ID 空间跨多个应用
- 真实案例：Airbnb 推送通知 IDOR 读全部私信、Facebook 支付卡信息 IDOR、Uber 改任意用户密码、PayPal 绕 2FA
